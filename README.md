# dsh-puzzle-mode · 拼图模式

> DSH（DeepSeek Harness）插件：把项目拆成 **主文档 + 若干模块文档**，让 AI 主动提问、
> 把不确定项变成已定项，并在输入框的**模型选择器左边**放一个显示**项目健康性**与五维的小按钮。

仓库：<https://github.com/liancha22/dsh-puzzle-mode>

不是独立模式：装进宿主组成后，**标准模式（或任何 preset）的会话**都带上它。

## 它做什么

**1. 一段宿主提示段 `puzzle-mode:policy`**（order 10500）——规定四件事：

- AI **主动提问**，一轮**最多 5 问**，优先给选项；
- **提问必须调 `ask_user_question` 工具**：在正文里写「① ② ③」**不算提问**——
  用户看不到可点选项，只能在聊天里手打。固定收尾问也走同一个工具；
- **每一次提问的最后固定问「要不要先停下？」**，两个选项：
  ① 停下，等我看过再说 → 只回写文档 + 一句话说明，本轮立即结束，不执行任何动作；
  ② 继续，不用停 → 按当前模式继续；
- **一个会话只绑一个项目**：绑定记在主文档 front-matter 的 `会话:` 数组里；没绑定就是空，
  **不会**自动占用别的会话的项目（早先「回退到最新项目」正是文档混成一团的根因）；
  新建项目时**一次同时创建 工作区文件夹 + 主文档 + 每个模块一份文档**，并自动绑定本会话；
- 两种执行模式的许可边界（见下）。

**2. 模型工具 `puzzle_mode`**

| op | 作用 |
| --- | --- |
| `list` | 列出现有项目（名字 / 模式 / 健康性 / 模块数 / 更新时间）并标出默认用哪个 |
| `read` | 读状态（不建文件）：项目、模式、模块、**五维健康性** |
| `show` | 读某个模块文档的详情（要点 / 悬而未决 / 已定 / 详细记录），不建文件 |
| `init` | 新建项目：文件夹 + 主文档 + N 份模块文档，一次建齐，并**自动绑定本会话**（从旧项目上解绑） |
| `bind` | 把**本会话**绑到已有项目（旧项目自动解绑）；一个会话只出现在一个项目里 |
| `unbind` | 解绑本会话，回到「没绑定」；**文档与文件夹都留着**，只动 front-matter 那一行 |
| `rebuild` | 重建/迁移**文档格式**：默认 dry-run 只报计划，`apply:true` 落盘；正文一字不动 |
| `main` | 更新主文档四节之一：`index` / `source` / `tools` / `pit` |
| `module` | 更新（必要时创建）模块文档：`progress` / `points` / `pending` / `decided` / `detail` |
| `health` | 写五维健康性（**必须带 `name`**，五维写在模块文档上） |
| `audit` | **按五维审查当前项目**：客观发现 + 最弱维度排序 + 写点评的指令 |
| `mode` | 切换执行模式 |

每次返回都带 `askPause: true` 与固定收尾问的原文（这是**宿主侧契约**，与面板提示词无关——
面板的提问/建项目/审查/迁移模板里都**不带**它，收尾问由模型按提示段自己带）。
每次返回还带 `projectSource` 与 `cwdSource`：

| `projectSource` | 含义 |
| --- | --- |
| `explicit` | 调用里显式给了 `project` |
| `bound` | 本会话绑定的项目（**唯一的默认来源**） |
| `none` | 本会话还没绑定 → `project` 为空串，不猜、不占用别人的项目 |

`cwdSource` 说明「项目根从哪来」（`session` / `process` / `fallback`）。
「用的是哪个项目」「项目根从哪来」都可见，不会静默选错。

返回里还带文档格式版本 `version` 与 `outdated`：`outdated: true` 表示这份文档是旧格式，
要 `op:rebuild` 迁移（见下）。

**3. 两种执行模式**

| 模式 | 提问 | 文档 | 执行（bash / write / edit …） |
| --- | --- | --- | --- |
| 只拼不写 | 可以（每次带固定收尾问） | 可以 | **禁止**（宿主 `tools/pre-execute` 返回 `deny`） |
| 边拼边写 | 小改动问一次、大改动问一次 | 可以 | 允许 |

拦截点是 `tools/pre-execute`（运行时官方钩子，`deny` 的理由会作为该次调用的错误回到模型）。
**不用 `agent/pre-step`**：那个事件的 `decision.messages` 契约是 `UserMessage[]`，里面没有 tool-call，
在它上面做拦截是永远不生效的死代码。

`write` / `edit` 有意**不在**白名单里——它们能绕过 `puzzle_mode` 的 slug 过滤与路径守卫。
v0.7.0 起更进一步：**文档锁**在任何模式下都拦它们（只要目标是 `拼图/` 下的文件）。

**4. 拼图面板 UI**

- `conversation.input.left`（模型选择器左边）小按钮：拼图图标 + 当前**项目健康性**百分比；
- 点开 `shell.overlay` 弹出面板：项目路径、健康性进度条、**五维条**（跨模块均值）、
  **模块图块**（未建的显示「未建」）；
- **图块可点开**：点模块块读该模块文档——要点 / 悬而未决 / 已定 / 详细记录**逐条成卡**
  （书签式），每条带序号、出处，不合规的当场标 `超N字` / `缺出处`；
- **提问模板**：一键把提问骨架填进输入框（`inputActions.setDraft`），**不自动发送**。
  模板里**只放问题槽位，不带固定收尾问**——收尾问由模型按提示段自己带；
- **审查**：另一颗按钮，填的是审查请求（先调 `op:audit` 拿事实，再按五维点名点评）；
- **迁移/重构**（常驻）：填的是「全量清理并重构到最新规格」的提示词，见「文档格式版本与重建」一节；
- **客观发现**直接列在面板里：三档（堵 / 补 / 提）+ 事实 + 下一步，不必先问 AI 才看得到；
  **条目级问题也在内**（哪一节有几条超长、几条没出处）；
- **新会话默认空**：面板显示空态。空态有三条路：
  **①表单直建**（填项目名/模块名/目标 → 点「立刻建」，直接调 RPC，**不经过模型**）、
  **②快速建空壳** / **③采访后再建**（把模板填进输入框由 AI 来建，不自动发送）；
  并列出已有项目可一键**绑定**，已绑定的项目可一键**解绑**；
- 项目下拉**切换即改绑**（不是临时查看）：一个会话只绑一个项目，切走就等于从旧项目上解绑；
- 模式切换写回主文档 front-matter，与工具口径同一份数据；
- 拿不到会话工作目录时（`cwdSource !== 'session'`）面板显式警告，不静默写错地方。

## 审查（op:audit）

审查分两半，**插件只做事实那一半**：

| 半边 | 谁产出 | 内容 |
| --- | --- | --- |
| 客观发现 | 插件（规则） | 从文档数出来的事实 + 一条可执行的下一步 |
| 点评 | **模型** | 一针见血的判断：最弱一维、缺哪条证据、整体最该补什么 |

返回里带 `findings`（每条含 `level` / `scope` / `fact` / `fix`）、`ranking`（五维升序）、
`prompt`（写点评的指令）。**插件不生成评价正文**——规则写不出人话，而「一针见血」要上下文。

三档严重度：

| level | 含义 | 例子 |
| --- | --- | --- |
| `blocker` | 数字与文档对不上，挡路 | 「完成度写 100，但要点 0 条」；模块文档 0 条内容 |
| `warn` | 该补 | 「手写代码质量 95 分，但对应证据 0 条」；**条目超长 / 没出处**；某节为空 |
| `info` | 提示 | 「五维全是公式推的，没有一处人工判断」；最弱一维是谁 |

### 条目级发现优先（v0.8.0）

v3 的字数上限与源码出处**只在写入时拦**——已经躺在文档里的长条目、无出处条目不会被追溯。
审查如果只看条数，就会说「要点 15 条，很充实」，而实际上 15 条全都超 20 字、全都没出处：
**数字漂亮，规格全破**。所以审查现在逐条验，产出两类发现：

| id | scope | fact 例 |
| --- | --- | --- |
| `entry_issue:<模块>:<小节>` | 模块 | 「模块「面板」的「## 要点」有 14 条超 20 字、1 条没出处」 |
| `main_entry_issue:<小节>` | project | 「主文档「## 坑」有 3 条超 20 字」 |

两类都必须**先清**：它们让「条数很多」变成假象。修法固定——
`op:main` / `op:module` 带 `append:false` 重写那一节，每条压到上限内并补上真实出处。

几处刻意的设计：

- **`never_reviewed` 全都没评估时只报一条项目级**，否则三个模块刷三条一样的。
- **`progress_no_points` 是 blocker**：完成度 100 而要点为空，是文档在装样子，不是小毛病。
- **可拓展性只看模块自己的悬而未决 / 已定**：v3 起主文档没有决策小节了，项目级决策没有载体。
  项目级证据只剩主文档的「坑」（供 `quality` 用）。

## 文档格式版本与重建（op:rebuild）

主文档 front-matter 里有个 `puzzle:` 字段，它是**文档格式版本**：

| 版本 | 形状 |
| --- | --- |
| `1` | 只有 `## 进度` / `完成度` 单一维度；模块 front-matter 带 `模式:`/`计划模块:`；**没有** `## 健康性`；主文档没有 `会话:` |
| `2` | 五维 `## 健康性`；模块 front-matter 只留 `项目:`/`模块:`；主文档有 `会话:` 绑定 |
| `3` | 主文档**只有四节**（模块索引 / 源码索引 / 工具索引 / 坑）；模块拆出 `## 悬而未决`（≤4）与 `## 已定`（≤10）并去掉勾选框；`## 撤销` 取消；条目限长且必须带源码出处 |

**为什么需要它**：插件有过两次破坏性改动（`完成度` → 五维、加会话绑定）。旧文档被读到
**不会报错**——只会「五维全靠推导、分数偏低」，问题静默存在。版本号 + 重建就是给这件事一条明路。

### 怎么用

```jsonc
{ "op": "rebuild" }                    // 预览：逐文件列出将要改什么，不写盘
{ "op": "rebuild", "apply": true }     // 落盘
```

`op:read` 里 `outdated: true` 就说明该迁移了；审查里也会有一条 `doc_outdated` 提醒。

面板上有**两颗**按钮，分工不同：

| 按钮 | 走谁 | 做什么 |
| --- | --- | --- |
| **迁移/重构**（常驻） | 模型 | 把整套提示词填进输入框：先 `op:rebuild` 落盘（改形状），再按规格**逐节重写正文**（压长度、补出处、删超限旧项），最后再跑一次 `op:audit` 确认条目级发现清零 |
| **仅迁移格式**（常驻） | 面板直接调 RPC | 只做机械动作：四节化、补小节、拆 悬而未决/已定。先出预览，确认后落盘；**正文一字不动** |

为什么要两颗：格式迁移是**确定性的**（面板自己就能做完，不必占一轮对话）；
而**正文重写**必须模型来做——旧条目超长、没出处、条数超限，`rebuild` 刻意不追溯，
只能由模型按规格逐条压。前者快，后者狠，别混在一起。

### 重建做什么、不做什么

| 做 | 不做 |
| --- | --- |
| 补版本号、`模块:` 字段 | 改用户写的正文（要点、详细记录一字不动） |
| 去掉模块文档上多余的 `模式:`/`计划模块:` | 改条目里的字（限长与出处校验**从下一次写入**才生效） |
| 补缺失的小节与 `## 健康性` | 自动绑定会话（空绑定就该是空的） |
| 把旧 `完成度` 折算成五维**起点** | 覆盖已有的证据或人工分数 |
| v2 → v3：主文档删掉 用户原话 / 悬而未决 / 已定 / 撤销，模块合并小节拆成两个 | 保留主文档里已取消的四节（**会真的丢内容**，预览里逐条列明） |

几处刻意的设计：

- **默认 dry-run**。本项目**不自动备份**（工作区通常在 git 里），预览就是唯一的刹车；
  预览与实际落盘是**同一份产物**，所以「看到的」就是「会做的」。
- **迁移期的条目搬移只去勾选框、只按上限删最旧，不校验字数与出处**。
  老文档的条目本来就没有 `（源码: …）`，若按新规则校验，整段内容会**静默变成「（待补）」**。
  迁移只改形状，新规则从下一次写入开始生效。
- **折算只填拿不到证据的维度**。某维已经能由文档推导出分，就**留空**——填了反而变成
  「显式声明」，把推导冻死在折算值上。所以有要点的模块根本不会被填数字。
- **折算一律 ×0.5**（`PROGRESS_TO_HEALTH`）。完成度只说明*做过*，不足以给高分；
  而且用五个不同的系数看着更"准"，其实是凭空编的比例。
- **幂等**：迁移完再跑是 0 改动、不写任何文件。
- **小节顺序按模板重排**。迁移是「拆分 → 改 → 按规范顺序拼回」，而不是逐个 `withSection`——
  后者找不到小节时会追加到末尾，把 `## 坑` 插到 `## 模块索引` 之前（实测踩过）。

## 面板直接建项目（不经过模型）

建一个空壳是**纯机械动作**：起文件夹、写主文档、按模块名各写一份。走模型要多花一整轮对话，
而走 RPC 是同步的——点完就绑好了。所以面板空态给了表单直建：

| 输入 | 说明 |
| --- | --- |
| 项目名 | **必填**，会经过宿主 `slugify`，并成为工作区里的文件夹名 |
| 模块名 | 可留空；按 `,` `，` `、` `;` `；` 与空格切分，空名与重复名由宿主去重 |
| 目标 | 可留空，写成主文档顶部的 `> 目标：…` |

点「立刻建」→ `POST /puzzle-mode-rpc { method: "create", project, modules, goal }`：
一次建出 **文件夹 + 主文档 + 每个模块一份文档**，并**自动绑定本会话**（从旧项目上解绑）。
模块名与项目名都会经过 `slugify`，路径经 `safeJoin` —— 表单直建不能绕过路径守卫。

两条路的分工：**表单直建**是「我想好了，立刻建」；**两个模板按钮**是「让 AI 来建」
（会问、会拆模块）。想改绑到别的已有项目，用项目下拉（切换即改绑）或空态里的「绑定」。

## 面板怎么显示文档

模块图块点开后，内容**不是一整块 `<pre>`，而是一条一张卡片**（书签式）：

```
要点（10 条，每条 ≤20 字 + 出处）
┌──┬─────────────────────────────────────────────┬──────────┐
│1 │ 主文档只有四节              lib/puzzle.js:153 │          │
│2 │ 这一条特别长特别长特别长特别长特别长特别长   │ 超9字·缺出处 │
│3 │ 没有出处的一条                               │ 缺出处    │
└──┴─────────────────────────────────────────────┴──────────┘
```

每条独立成卡，左侧序号、右侧出处、**不合规的当场标出来**（`超N字` / `缺出处`，边框转警告色）。
理由：一整个 `<pre>` 读起来像读源码，条目之间没有边界；拆开之后每条可单独扫，
审查报告说「要点有 5 条超长」时，面板里能直接看到**是哪 5 条**。

## 一个会话只绑一个项目

绑定是**文档自带**的，不是插件侧的状态文件：主文档 front-matter 里多一行

```yaml
---
puzzle: 1
项目: 拼图模式插件
模式: 边拼边写
计划模块: ["会话绑定","面板"]
会话: ["<sessionId>"]        # ← 这一行；没绑定时整行不写
更新时间: 2026-09-26 14:30:00
---
```

为什么放文档里：**归属跟着文档走**。复制项目、换 profile、把工作区拷到别的机器，绑定都还在；
插件侧不用维护第二个真源，也不会出现「文件丢了但文档还在」的半截状态。

解析顺序只有三步，**没有第四步**：

```
显式 project  >  本会话绑定的项目  >  空（project: ""）
```

早先还有一步「回退到项目根下最新修改的项目」。那一步会把新会话直接塞进上一个会话的项目，
越写越混——一个项目里攒着好几摊互不相干的活儿。现在没绑定就是空：
`op:read` 回 `initialized: false`，面板显示空态，明确要求新建或绑定。

绑定写入有三个入口，都走同一个 `bindSession`（**先解绑旧项目，再绑新项目**）：

| 入口 | 场景 |
| --- | --- |
| `op:init` | 建项目 = 顺带绑定本会话，并从别的项目上解绑 |
| `op:bind` | 绑到已有项目（只给 `project`，不重建） |
| 面板按钮 | 空态的「绑定」与项目下拉的切换 |

「一个会话只绑一个」约束的是**会话侧**：同一项目可以被多个会话绑定（串行改同一摊活儿），
但一个会话不能同时挂在两个项目上。

## 文档布局

```
<会话工作区>/<项目名>/拼图/
├── 主文档.md                 # 只有四节：模块索引 / 源码索引 / 工具索引 / 坑
└── 模块/
    ├── auth-flow.md
    └── session-store.md
```

主文档**固定四节**：`## 模块索引`、`## 源码索引`、`## 工具索引`、`## 坑`——
**除这四节外不写任何内容**。用户原话不再入库（提问的回答只以几句精简结论进模块文档），
撤销项直接删除，决策只写在模块文档里，轮汇报写进模块的 `## 详细记录`。

条目格式固定为「一句话（源码: 文件:行）」——**查找方向是 主文档 → 源码**，所以每条都能回查。
字数上限只算「（源码…」之前的那句话，出处不占额度：

| 位置 | 上限 | 条数上限 |
| --- | --- | --- |
| 模块索引 / 源码索引 / 工具索引 | 50 字 | — |
| 坑 | 20 字 | — |
| 模块 `## 要点` | 20 字 | — |
| 模块 `## 详细记录`（轮汇报） | 50 字 | — |
| 模块 `## 悬而未决` | 20 字 | **4 条**，超了删最旧 |
| 模块 `## 已定` | 20 字 | **10 条**，超了删最旧 |

**超长是报错，不是截断**——半句话落进文档比让模型重写一遍更糟。
**超条数是自动删最旧**，不论旧项有没有澄清（这是用户定的硬规则）。

### 文档锁：拼图文档只能由 `puzzle_mode` 改

`write` / `edit` / `str_replace_editor` 只要目标是 `拼图/` 下的文件，宿主就会 **deny**——
**所有模式都一样**（`边拼边写` 也拦）。原因：文档形状由 `puzzle_mode` 统一维护
（条目限长、条数上限、slug 过滤、路径守卫），一次 `write` 覆盖就能把这些规则全跳过。
只读仍然自由：`read` / `grep` / `glob` / `op:show`。

## 项目健康性怎么算

五个维度，**每一维 0-100、越高越好**（含「维护系数」——高分表示维护负担轻）：

| 维度 | 含义 |
| --- | --- |
| 任务复杂度 | 模块实际承担的任务量；记下的要点与细节越多越完整 |
| 可拓展性 | 还能往哪里长：悬而未决与已定越多，扩展空间越清晰 |
| 维护系数 | 维护负担轻的程度（高分 = 好维护）：要点写清了才敢改 |
| 代码质量 | 坑与决策的沉淀程度：踩过的坑记下来了，质量才站得住 |
| 可复用性 | 有多少可被别处复用的东西（共享模块、公共接口、抽象） |

**两条取值路径，显式优先：**

1. **显式写**：模块文档的 `## 健康性` 里一行一维，如 `任务复杂度: 80`。
   写 `维护成本: 30`（成本型）会被自动翻成 `维护系数: 70`。
2. **由文档证据推导**（没写时）：从 `## 要点`、`## 详细记录`、`## 悬而未决`、`## 已定`、主文档的 `## 坑` 计数推导。

```
任务复杂度 = 要点×12 + 详细记录×10
可拓展性   = (悬而未决 + 已定)×20
维护系数   = 要点×18 + 详细记录×8
代码质量   = 坑×25 + 已定×15
可复用性   = 共享条目×30 + 要点×10

模块健康性 = 五维均值
项目健康性 = 各模块健康性的均值
```

**跨层级证据**：`代码质量` 用主文档的「坑」（v3 里主文档只剩这一个内容节，坑是项目级证据）；
`可拓展性` 用模块自己的「悬而未决 / 已定」——主文档不再有决策小节，项目级决策没有载体了。

**这是设计意图，不是缺陷**：健康性反映的是「已经写在文档里的证据」，不是模型凭感觉打的印象分。
空模块五维全 0——不是"看起来还行给 60"。想让数字涨，就真的把内容写进去。

返回里带 `sources`（每维是 `module` / `derived`），面板据此能区分
"评估过的" 和 "公式推出来的"。项目健康性由宿主汇总，**不要在文档里手写总分**——
v3 的主文档只有四节，连写它的地方都没有（`op:health` 不带 `name` 会被拒绝）。

## 安装

包内声明了 `dsh.bundle.patch`，`dsh plugin add` 会自动把这一行插进 profile 组合，`remove` 自动移除：

```yaml
- insert:
    - id: dsh-puzzle-mode
      name: 'dsh-puzzle-mode'
```

**A. 从 GitHub（推荐，仓库必须 public）**

```bash
# 1) 插件管理器（App 插件页「添加插件」用的就是它；支持标签/分支/子目录）
python3 "$DSH_HOME/plugin-manager.py" github liancha22 dsh-puzzle-mode
python3 "$DSH_HOME/plugin-manager.py" github liancha22 dsh-puzzle-mode v0.1.0   # 指定标签/分支
python3 "$DSH_HOME/plugin-manager.py" github liancha22 dsh-puzzle-mode main/lib # 分支 + 子目录

# 2) dsh CLI 走 pnpm，只认 npm 名或 git 协议（不认 owner/repo）
dsh plugin --profile web add github:liancha22/dsh-puzzle-mode
```

装完**重启该 profile**（`patchReload: startup`），然后刷新浏览器页面。
卸载：`dsh plugin --profile web remove dsh-puzzle-mode`。

**B. 本地目录（开发 / 自测）**

```bash
git clone https://github.com/liancha22/dsh-puzzle-mode ~/.dsh/plugin-src/dsh-puzzle-mode
ln -s ~/.dsh/plugin-src/dsh-puzzle-mode <profile>/node_modules/dsh-puzzle-mode
# 然后在 <profile>/package.json 里加：
#   dependencies:        "dsh-puzzle-mode": "link:/abs/path/to/dsh-puzzle-mode"
#   dsh.profile.bundles: [ ..., "dsh-puzzle-mode" ]
```

本插件不发布任何 Cordis 服务，只消费 `tools` / `systemPrompt` / `webServer` / `sessions`，

`/sdcard` 这类 FUSE 挂载上读取略慢，源码更适合放在 `plugin-src` 或硬盘目录。

**离线 / 手工**：把 `cordis.patch.yml` 里的 `insert` 段合并进 profile 的 `cordis.patch.yml`（用户补丁层在 bundle 层之后生效）。

### v3 的验收判据（交给真机，不写自检）

v0.8.0 的面板与审查：

- 解绑后点「⟳ 刷新」→ 仍是空态；

### 一个值得记住的教训

拦截最初写在 `agent/pre-step` 上，并且测试是**绿的**——但那是假绿：
`agent/pre-step` 的 `decision.messages` 契约是 `UserMessage[]`，里面根本没有 tool-call，
所以真实运行时永远走不到那个分支，而测试自己伪造了一条带 tool-call 的 assistant 消息。
换成 `tools/pre-execute`（真实契约：返回 `{kind:'deny',reason}`）后，断言才对得上真实行为。
**写测试时要用权威契约的形状，不要用自己以为的形状。**

### 另一个：闭包会记住你解绑之前的项目

「解绑了过一会又自动绑定」有两个独立的成因，**两个都得修**，只修一个症状会变形：

1. **面板轮询带上了闭包里的旧项目名**。`useEffect` 的依赖是
   `[open, sessionId, props.sessionId]` —— 解绑不会让它重跑，所以 8 秒一次的定时器
   永远握着「解绑前那个项目」。而显式 `project` 在宿主侧的**优先级高于绑定**，
   于是解绑 8 秒后面板又显示成已绑定。修法：轮询与刷新**只发 `sessionId`**，
   让宿主按绑定解析——归属只有一个真源，面板不该替宿主记着。
2. **`createProject` 无条件重绑**。项目已存在时再走一次 `op:init`（模型把「建项目」
   当成幂等的「确保存在」，很常见），会把刚解绑的会话重新写回 `会话:` 行。
   修法：**只在主文档是这次新建的时候才绑**，并返回 `rebound` 让调用方如实回报。

教训：**「谁记得状态」只能有一个**。面板记一份、文档记一份，两边就会打架；
而带旧状态的闭包是这类 bug 的温床——定时器尤其危险，因为它活得比一次渲染久。
